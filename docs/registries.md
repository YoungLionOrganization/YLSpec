# Registry accounts and publishing

GitHub Releases distribute all built assets. Publishing to PyPI, npm, Maven
Central, and Visual Studio Marketplace additionally requires control of those
registries' accounts and namespaces. A GitHub organization does not automatically
create an npm organization, a Central namespace, or a Marketplace publisher.

## GitHub secret locations

Open [repository Actions secrets](https://github.com/YoungLionOrganization/YLSpec/settings/secrets/actions),
then **New repository secret**. Use the names below exactly. Paste each value
directly into GitHub's secret field, never into source files, issues, or logs.

| Secret | Registry | Value |
|---|---|---|
| `PYPI_API_TOKEN` | PyPI | A PyPI token authorized to publish `ylspec` |
| `NPM_TOKEN` | npm | Granular token with package/scope publishing access and publishing 2FA bypass |
| `MAVEN_CENTRAL_USERNAME` | Maven Central | Username generated by Central Portal's user-token dialog |
| `MAVEN_CENTRAL_PASSWORD` | Maven Central | Password generated with that same user token |
| `MAVEN_GPG_PRIVATE_KEY` | Maven Central | ASCII-armored OpenPGP secret key used to sign the artifacts |
| `MAVEN_GPG_PASSPHRASE` | Maven Central | The signing key's passphrase; empty only for an unprotected key |
| `VSCE_PAT` | Visual Studio Marketplace | Marketplace publishing credential accepted by `vsce` |

`GITHUB_TOKEN` is supplied automatically by GitHub Actions. It is not an npm,
PyPI, or Central credential. Publishing workflows use secrets only in the jobs
that upload distributions; ordinary verification does not require registry keys.

## PyPI

The `publish.yml` workflow uses the existing `PYPI_API_TOKEN` secret and the
`pypi` GitHub environment. Create the token from
[PyPI account settings](https://pypi.org/manage/account/#api-tokens). Prefer a
project-scoped token once the `ylspec` project exists. For initial project
creation, PyPI may require an account-scoped token; replace it with a scoped
token after the first upload. Store the complete token, including its prefix.

The workflow rebuilds the pinned commit, verifies all targets, creates a draft
GitHub Release, uploads the Python distributions, then makes the release public.
Existing PyPI filenames are skipped only after checking their reported SHA-256.
See [publishing](publishing.md) for recovery and version policy.

## npm: JavaScript and TypeScript

Package: `@younglionorganization/ylspec`.

1. Sign in to [npm](https://www.npmjs.com/) and create or obtain publishing access
   to the `younglionorganization` npm organization/scope. Verify the account's
   email and enable the authentication required by npm.
2. Open **Profile → Access Tokens → Generate New Token**.
3. Choose a granular token. In **Packages and scopes**, grant **Read and write
   (publish and stage)** to the `@younglionorganization` scope or the existing
   `@younglionorganization/ylspec` package. An organization-management grant alone
   does not permit publishing packages.
4. Enable **Bypass two-factor authentication** for noninteractive publishing.
   A stage-only token cannot finish this direct-publish workflow. The package's
   publishing policy must allow granular tokens.
5. Copy the generated token once and store it as `NPM_TOKEN` in GitHub.
6. After the GitHub Release is public, run **Actions → Publish npm package → Run
   workflow** on `main`. Enter `0.1.1`, or leave the version empty to use
   `release/release.json`.

The workflow downloads the published release tarball and verifies its SHA-256
before uploading it. It does not rebuild native binaries during publication.
Users install it with:

```sh
npm install @younglionorganization/ylspec
```

Registry policy is time-sensitive: npm currently documents the removal of
direct publishing with bypass-2FA granular tokens in January 2027. Before that
transition, migrate this upload step to npm Trusted Publishing, or adopt a
stage-only token plus maintainer promotion. This date comes from
[npm's access-token policy](https://docs.npmjs.com/about-access-tokens/), rather
than a guarantee by this project. The current setup follows
[npm's token-creation instructions](https://docs.npmjs.com/creating-and-viewing-access-tokens/).

## Maven Central: Java, Kotlin, and Android

Namespace: `io.github.younglionorganization`.

| Artifact | Contents |
|---|---|
| `ylspec` | Shared Java API; runtime dependency on desktop native resources |
| `ylspec-kotlin` | Idiomatic Kotlin helpers over the Java API |
| `ylspec-natives` | Desktop JNI resources for the verified OS/architecture targets |
| `ylspec-android` | JNI-only AAR for four Android ABIs, minimum API 26 |

1. Sign in to [Central Publisher Portal](https://central.sonatype.com/).
2. Add and verify the exact namespace `io.github.younglionorganization` using
   the Portal's ownership procedure. Follow the
   [namespace guide](https://central.sonatype.org/register/namespace/); organization
   ownership may require verification beyond a personal GitHub login.
3. Open [User tokens](https://central.sonatype.com/usertoken) and choose
   **Generate User Token**. Save the two generated credentials as
   `MAVEN_CENTRAL_USERNAME` and `MAVEN_CENTRAL_PASSWORD`. These are Portal token
   values, not the account's login password. See
   [token guidance](https://central.sonatype.org/publish/generate-portal-token/).
4. Create or choose an OpenPGP signing key. Publish its public key according to
   [Central's GPG requirements](https://central.sonatype.org/publish/requirements/gpg/).
   Store the ASCII-armored secret-key export as `MAVEN_GPG_PRIVATE_KEY` and the
   key passphrase as `MAVEN_GPG_PASSPHRASE`.
5. Run **Actions → Publish Maven Central libraries → Run workflow** on `main`
   after the GitHub Release is public.

For a new signing key, these GPG commands are run by the key owner on their
trusted signing machine. Replace the key fingerprint with the one reported by
GPG, rather than copying a placeholder into a secret:

```sh
gpg --full-generate-key
gpg --list-secret-keys --keyid-format long
gpg --armor --export-secret-keys YOUR_KEY_FINGERPRINT
gpg --keyserver hkps://keyserver.ubuntu.com --send-keys YOUR_KEY_FINGERPRINT
```

Keep the secret-key output private. A public-key upload is different from a
secret-key export. The workflow imports the secret into a temporary GPG home,
signs the already verified artifact bytes, adds checksums, and submits a Maven
layout bundle through the
[Central publishing API](https://central.sonatype.org/publish/publish-portal-api/).
It records the deployment identifier and waits for the Portal's publication
result. The namespace must be verified before uploading.

See the [Java/Kotlin/Android guide](../jvm/README.md) for dependency declarations,
including exclusion of desktop natives from Android applications.

## Visual Studio Marketplace

Publisher identifier: `YoungLionOrganization`; extension name: `ylspec`.

1. Create that publisher at the
   [Marketplace publisher management page](https://marketplace.visualstudio.com/manage).
   Its identifier must match `editors/vscode/package.json`. If the identifier is
   unavailable, update the manifest and documentation together before packaging.
2. Follow the current
   [VS Code publishing authentication guide](https://code.visualstudio.com/api/working-with-extensions/publishing-extension).
   For PAT-based publishing, create an Azure DevOps credential with Marketplace
   **Manage** permission and publisher access, then store it as `VSCE_PAT`.
   Microsoft documents retirement of global Azure DevOps PATs on December 1,
   2026; follow its Entra ID migration guidance when that applies to the account.
3. Run **Actions → Publish VS Code extension → Run workflow** on `main` after
   the GitHub Release is public. The workflow uploads the checksummed VSIX.

Marketplace account setup is separate from installing the VSIX. Users can
already install a verified release VSIX through **Install from VSIX…**.

## Version and failure rules

All assets use the library release version from `release/release.json`; document
format and frame versions stay 0.1. Each registry workflow accepts an existing
public GitHub Release version, and verifies the corresponding asset digest.
Missing credentials, incomplete namespace setup, missing assets, or failed
registry validation stop that upload. They do not convert an unverified build
into a release. Registry versions are immutable; use a new patch version when
published content needs to change. Check a deployment's recorded status before
retrying after a network timeout.
